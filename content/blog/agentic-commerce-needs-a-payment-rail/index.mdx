The first version of AI shopping looked like a better search box.

Ask for running shoes, a flight, or a camera. The assistant finds options, summarizes them, and sends the human to a checkout page. That is useful, but it is still a recommendation interface with a conversational front end.

Agentic commerce starts when the agent can complete the purchase.

That changes the architecture. A recommendation can be wrong and annoying. A payment can be unauthorized, duplicated, disputed, or sent to the wrong merchant. The system now needs a durable representation of intent, a way to bind that intent to a specific cart, a payment credential that is safe to delegate, and an audit trail that survives several companies and protocols.

The market is moving in that direction. On September 9, 2026, [Mastercard announced Agent Connect](https://www.mastercard.com/us/en/news-and-trends/press/2026/september/mastercard-gives-merchants-a-simpler-way-to-build--connect-and-s.html?et_cid=233333&et_mid=6331618&et_subid=23677216), describing a single integration point for merchants, AI agents, digital platforms, and payment providers. The announcement separates product discovery, cart confirmation, and secure completion using consumer-authorized credentials. [EMVCo released a draft framework](https://www.emvco.com/news/emvco-requests-feedback-on-framework-for-secure-interoperable-and-scalable-card-based-agentic-payments/) that focuses on delegated authority, recurring purchases, cumulative budgets, and intent state shared across participants.

The important signal is not that another commerce API exists. It is that intent is becoming a protocol object.

## A purchase is a state machine

A natural-language request is too vague to be a payment authorization.

“Find me a good laptop under 1,000 dollars” expresses a goal. It does not authorize an arbitrary laptop, a subscription, an extended warranty, or a seller that the user did not approve. The agent must turn the goal into a proposed purchase, then ask the user—or a previously configured policy—to approve a bounded action.

The lifecycle looks like this:

~~~text
goal
  -> candidate set
  -> selected cart
  -> price and fulfillment confirmation
  -> delegated authorization
  -> payment authorization
  -> settlement
  -> delivery and dispute state
~~~

Each transition can invalidate the previous one. A price change should not silently inherit approval. A changed delivery address should trigger a new check. A recurring purchase needs an authority window and cumulative limit.

This is why a payment rail matters. The commerce system needs a shared, verifiable state machine rather than a sequence of natural-language messages.

## Discovery, authorization, and settlement are different planes

A robust system keeps three planes separate:

1. **Discovery.** What products exist, who can sell them, what is available, and which merchant rules apply.
2. **Authorization.** What the consumer delegated, to which agent, for which merchant, with what budget and expiration.
3. **Settlement.** How a payment credential is tokenized, authorized, captured, refunded, and disputed.

The agent can participate in all three, but it should not own all three. Product data should remain merchant-controlled. Authority should remain user- or issuer-controlled. Settlement should be enforced by the payment network or processor.

The architecture can be expressed as:

~~~text
merchant catalog -> agent discovery -> cart proposal
                         |
                         v
                 intent policy engine
                         |
                         v
                 tokenized payment rail
                         |
                         v
              authorization / capture / dispute
~~~

The arrows are not merely data flows. Each is a trust boundary.

## Intent needs a durable, typed shape

The intent object should be explicit enough for a policy engine to evaluate and compact enough to travel between participants.

~~~ts
type PurchaseIntent = {
  intentId: string
  principal: string
  agent: string
  merchant: string
  items: Array<{
    productId: string
    quantity: number
    maxUnitPriceMinor: number
  }>
  currency: string
  maxTotalMinor: number
  allowedFulfillment: string[]
  expiresAt: string
  repeatPolicy?: {
    maxOccurrences: number
    windowEndsAt: string
  }
  approval: {
    mode: "explicit" | "preapproved"
    evidenceId: string
  }
}
~~~

This is not a universal schema. It illustrates the engineering boundary: the intent is inspectable, constrained, expirable, and auditable.

The payment system should never infer those fields from the agent's final prose. The agent may explain the purchase in natural language, but the rail should evaluate the typed object.

## Tokenization is necessary but not sufficient

Delegating a raw card number to an agent would be an architectural mistake. The capability should be tokenized, scoped, and revocable.

The token should bind to as much context as the payment ecosystem can reliably validate:

- principal and agent identity;
- merchant or merchant category;
- cart or order reference;
- amount and currency;
- time window;
- recurring limits;
- channel and device;
- approval evidence;
- replay protection.

EMVCo's draft framework calls out the need to manage intent over time and coordinate state across participants. That is the hard part of recurring and cumulative purchases. A static bearer token cannot express “you may buy up to 200 dollars from this merchant over the next seven days, but ask again if the shipping address changes.”

Authority must be evaluated at the moment of action, not only when the agent begins planning.

## Merchant control is a product requirement

The agent is not the merchant's new storefront. It is a client of the merchant's commerce policy.

Merchants need to control:

- which catalog attributes agents can access;
- how prices and promotions are represented;
- whether stock can be reserved;
- which fulfillment options are valid;
- whether a recommendation can use the brand;
- how a refund or cancellation is initiated;
- what customer relationship data is shared.

Mastercard's announcement makes this merchant-control point explicit: participating businesses can choose where and how they connect while maintaining control over pricing, fulfillment, customer relationships, and business rules.

That suggests an agent-facing commerce contract with policy fields, not only product JSON:

~~~json
{
  "product": {
    "id": "sku-431",
    "price": 79900,
    "currency": "INR",
    "availability": "in_stock"
  },
  "agent_policy": {
    "may_recommend": true,
    "may_reserve": false,
    "requires_price_confirmation": true,
    "max_cart_age_seconds": 120
  }
}
~~~

The customer experience should reflect those policies. If the price changed or the cart expired, the agent should say so instead of attempting a silent retry.

## Idempotency and disputes are first-class

An agent can retry because a network request timed out. A payment processor can retry because a downstream response was lost. Without a stable idempotency key, the same order can be captured twice.

Use an order-level key that is stable across retries but scoped to one intended operation:

~~~text
idempotency_key =
  hash(intent_id, cart_hash, merchant_id, operation, attempt_epoch)
~~~

The rail must record whether the key was:

- accepted and pending;
- authorized;
- captured;
- rejected;
- already completed;
- expired.

The agent should not invent a new key simply because the response was slow.

Disputes require the same depth of provenance. If a consumer claims that an agent purchased the wrong item, the system should reconstruct:

- the original goal;
- the selected candidates;
- the cart and final price;
- the authority that was active;
- the approval evidence;
- the exact request sent to the merchant;
- the authorization and capture results.

That is an execution trace, not a chat transcript.

## The market is assembling the rail

Worldline announced an agentic-commerce payment handler for the [Universal Commerce Protocol](https://worldline.com/en/home/top-navigation/media-relations/press-release/pr-2026_09_14_01), describing a way for merchants to declare payment configuration once and accept multiple payment methods across connected AI platforms. Mastercard is working on connectivity and merchant controls. EMVCo is asking the industry to review a framework for shared intent semantics.

These efforts may converge, compete, or be replaced. The stable engineering lesson is independent of the winning brand: commerce agents need interoperable intent and authorization semantics.

A product team should avoid hard-coding its business logic to a model vendor or a single agent surface. Keep the internal contract centered on:

- intent;
- capability;
- cart;
- authorization;
- settlement;
- evidence.

Adapters can then translate that contract to different marketplaces or payment providers.

## The user experience should feel more deliberate, not more magical

“Magic” is a weak requirement for a payment system. The user should know:

- what the agent found;
- why it selected the item;
- the final total;
- the merchant and fulfillment terms;
- which authority is being used;
- what can still change;
- whether confirmation is required.

Good agentic checkout may feel slower than a one-click purchase because it makes the important state visible. That is a feature. Trust is not the absence of a confirmation screen; it is confidence that the confirmation means what it says.

The agent can reduce friction by preparing the cart, comparing options, and explaining tradeoffs. The payment rail should still enforce the boundary.

## The architectural bet

Agentic commerce will not be won by the most persuasive shopping assistant. It will be won by the systems that can carry intent from conversation to settlement without losing scope, consent, or accountability.

That means treating payments as infrastructure for agents:

1. Represent intent as typed state.
2. Separate discovery, authorization, and settlement.
3. Use scoped, expiring payment capabilities.
4. Keep merchant policy authoritative.
5. Make retries idempotent.
6. Preserve evidence for disputes.
7. Show the user the boundary before the agent acts.

The chat interface is only the entry point. The payment rail is where agentic commerce becomes real.
