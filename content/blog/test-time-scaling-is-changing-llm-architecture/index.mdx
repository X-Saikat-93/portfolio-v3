For years, the default picture of an LLM was a function with one obvious shape:

~~~
prompt -> model -> completion
~~~

The model could be made larger, trained on more data, or served with lower latency. Inference was mostly the price of asking the model to run once.

Test-time scaling changes the object being engineered. A difficult request may now be answered by spending more compute at inference: extending a reasoning trace, sampling multiple candidates, searching over partial prefixes, calling a verifier, or escalating to a stronger policy. The output is not merely the result of a model. It is the result of a model plus an inference protocol.

That is a deeper shift than “reasoning models use more tokens.” It changes the architecture of serving, the shape of the cache, the scheduler's job, the meaning of latency, and the way we should report model quality.

## The new object is a search procedure

The most useful abstraction is a tree. The prompt is the root. Each generated token or reasoning step extends a prefix. A system can then:

- continue one trajectory until it reaches a terminal answer;
- sample several complete trajectories and choose by vote or score;
- branch from promising prefixes and prune weak ones;
- ask a verifier to evaluate candidates;
- stop early when a candidate passes a sufficient check;
- spend more compute only when uncertainty or task difficulty warrants it.

The recent paper [Test-Time Scaling in Reasoning LLMs: Inference Regimes, Evaluation, and Reproducibility](https://arxiv.org/abs/2608.04001), published in August 2026, makes an important distinction between sequential single-trajectory scaling, leaf-level scaling with terminal reduction, and prefix-level scaling. Those are not interchangeable implementations. They have different cache behavior, different failure modes, and different ways of accounting for compute.

Calling all of them “high reasoning effort” hides the architecture.

## A reasoning request has more than one budget

A practical system has at least five budgets:

1. **Policy budget** — how many tokens the model may generate while proposing a path.
2. **Branch budget** — how many independent candidates or prefixes may be explored.
3. **Verifier budget** — how much computation is available for checking candidates.
4. **Latency budget** — how long the user is willing to wait.
5. **Memory budget** — how much KV cache, host memory, and intermediate state can remain live.

These budgets trade against each other. Ten short candidates may be cheaper than one very long trajectory, but only if the verifier can compare them. Prefix sharing can reduce repeated prefill, but it increases scheduler and cache bookkeeping. A deeper search can find a better answer while making the tail of the latency distribution unacceptable.

The model's token limit is therefore not the same thing as the system's compute budget. A platform should make the protocol explicit rather than leaving it to an ambiguous reasoning-effort flag.

## Architecture: policy, state, verifier, scheduler

I think of inference-time scaling as four cooperating components.

### 1. The policy generates possible futures

The policy model proposes the next step. It may be a single model with a configurable thinking budget, a small model that produces many candidates, or a router that selects among models based on task shape. The policy is not required to decide the final answer immediately; it is exploring a state space.

### 2. The state store keeps prefixes and evidence

Every branch has a prefix, tool results, intermediate artifacts, and resource accounting. A naive implementation stores each candidate as an independent text string and recomputes the prompt from scratch. That works until the branch factor grows.

The serving system should represent shared prefixes explicitly:

~~~ts
type SearchNode = {
  id: string
  parentId: string | null
  prefixHash: string
  status: 'open' | 'expanded' | 'pruned' | 'verified' | 'selected'
  depth: number
  tokenCost: number
  verifierScore?: number
  children: string[]
}
~~~

The prefix hash is not just an optimization key. It identifies a reusable computation boundary. If several candidates share a prefix, the runtime should be able to share or reference the corresponding KV cache instead of paying the same prefill cost repeatedly.

### 3. The verifier turns plausibility into evidence

A verifier can be a formal checker, a compiler and test suite, a retrieval-grounded consistency check, a process reward model, or another language model. The right verifier depends on the task. A code patch can be compiled. A mathematical answer can be checked symbolically. A research answer can be checked for source coverage and contradictions.

The verifier is not automatically a source of truth. Correlated candidates can all satisfy a weak verifier. A language-model judge can reward fluent nonsense. A unit test suite can miss an untested edge case. A serious design records what was checked, with which version, and against which evidence.

### 4. The scheduler allocates the next unit of work

The scheduler decides whether to expand a prefix, run a verifier, prune a branch, or stop. This is the component that turns “think harder” into an actual policy.

It should understand marginal value. If a branch has low probability of beating the current best candidate and a high verifier cost, expanding it may be wasteful. If the task is cheap and uncertain, parallel candidates may be worthwhile. If the deadline is near, the scheduler should return the best verified result it has rather than start another branch that cannot finish.

## KV cache becomes a search data structure

Standard decoding already treats the key-value cache as a performance-critical memory region. Test-time search makes its ownership and lifetime more complicated.

With independent sampling, each candidate creates additional decode state. With prefix-level search, multiple branches share early states and diverge later. With tool use, an external observation changes the prompt and may invalidate part of the assumed continuation. With speculative or verifier-guided decoding, the system can generate and reject tokens at different rates.

That creates four engineering questions:

- **Locality:** Can a branch stay close to the worker holding its parent prefix?
- **Eviction:** Which branches can be recomputed, and which would be too expensive to lose?
- **Isolation:** Can one tenant infer the existence or content of another tenant's cached prefix?
- **Accounting:** Does cache memory count against the same budget as generated tokens?

Inference servers are already moving toward disaggregated prefill and decode because the two phases have different resource profiles. Test-time search adds another layer: a scheduler has to place a changing tree of work onto those workers while preserving useful prefix locality. A serving topology designed only for one linear decode path will leave performance on the table.

## Longer reasoning is not always better reasoning

More compute expands the search space, but it does not guarantee that the search finds a better answer. Long traces can accumulate errors, repeat a mistaken assumption, or spend the budget explaining a path that should have been discarded early.

The paper [First Finish Search](https://arxiv.org/abs/2505.18149) is a good reminder that simple early-stopping strategies can be surprisingly strong on some reasoning tasks. Its result is not a universal recipe. It demonstrates that the *shape* of the inference policy matters: when to stop and which candidate to trust can be as important as how many tokens are available.

This is also why the verifier should be a first-class component. If the system cannot distinguish an improving branch from a verbose branch, extra compute becomes extra latency.

## A request should be able to escalate

Most requests do not need a search tree. The right production policy is usually adaptive:

~~~
fast path
  -> direct answer when confidence and task class permit
  -> one verifier for structured or high-impact output
  -> parallel candidates for ambiguous reasoning
  -> deeper prefix search for hard cases
  -> human review when the remaining uncertainty is consequential
~~~

This policy should be learned from task-level evidence, not from a generic desire to maximize reasoning tokens. Useful signals include input structure, historical failure modes, tool availability, verifier disagreement, deadline, and the cost of a wrong answer.

The model can propose that it needs more thinking, but the runtime should decide whether more compute is allowed. The runtime owns the budget, the deadline, and the side effects.

## Evaluation must name the protocol

“Model X scored 85% with test-time scaling” is incomplete. A reproducible report should specify:

- model checkpoint and decoding parameters;
- number of candidates or search branches;
- maximum and average generated tokens;
- verifier model or deterministic checker;
- pruning and early-stop rules;
- cache reuse and recomputation behavior;
- wall-clock latency and hardware;
- total token, GPU, CPU, and verifier cost;
- failure and timeout handling;
- whether the reported number is pass@1, majority vote, best-of-n, or a verified selection.

The August 2026 inference-regimes paper makes this point directly: the evaluated object is the entire inference system, not only the policy model. It also separates exact replay from distributional reproducibility. That distinction matters when a search procedure is stochastic and a small change in scheduling alters which branches receive budget.

The same logic applies to safety. [OpenAI's work on chain-of-thought monitorability](https://openai.com/index/evaluating-chain-of-thought-monitorability/) studies how monitorability behaves as reasoning effort and model capability change. More inference compute can create more evidence for oversight, but it can also create a larger surface area to monitor. A system that stores only the final answer throws away the trajectory needed to understand what happened.

## What changes for architects

Test-time scaling moves several decisions out of model training and into platform architecture.

### Serving becomes search-aware

Schedulers need branch priorities, prefix locality, verifier queues, cancellation, and cache-aware admission. GPU batching is still important, but it is only one dimension of the scheduler's objective.

### Model APIs need protocol metadata

An inference response should be able to carry candidate identifiers, parent-prefix references, usage by phase, verifier status, and a reason for stopping. A string-only completion API encourages the application to rebuild this information badly.

### Cost becomes a quality control

The product should decide where extra compute has positive expected value. A support answer may need a fast retrieval check. A migration plan may need several candidates, a static analysis pass, and human approval. The expensive protocol belongs where an error is expensive—not on every request by default.

### Logs need to be trajectories

Store enough information to reconstruct the search: branch creation, pruning reason, verifier input and result, cache hit or miss, budget consumption, and selected path. Sampling only final responses hides the decisions that control quality and cost.

## The next model endpoint is a compute contract

The important API question is no longer only “Which model should answer?” It is “What inference procedure is allowed to answer, under which budget, with what evidence?”

That contract can remain simple to callers. A product might expose a mode such as “quality: balanced” or “quality: deep.” Internally, those modes should map to explicit budgets, search policies, verifier requirements, and latency ceilings. The abstraction is useful only if the runtime can observe whether it honored the contract.

Test-time scaling is changing LLM architecture because the architecture now includes the act of thinking at inference. Models still generate tokens, but production systems increasingly decide how many futures to explore, which ones to verify, what state to retain, and when additional compute has stopped paying for itself.

The next scaling law may be measured in parameters. It may also be measured in the quality of the search wrapped around them.
