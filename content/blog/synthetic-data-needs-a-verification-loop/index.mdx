Synthetic data is often sold as an answer to a supply problem.

Human-labelled examples are expensive. Privacy restrictions make some data difficult to share. Long-tail cases are rare. A capable model can generate more examples than a team could collect manually, so the obvious move is to use the model as a data factory.

The factory metaphor is incomplete. A generator can produce volume quickly, but it cannot certify that the volume contains the information the next model needs.

The production problem is not generation. It is controlled feedback.

The [ICLR 2026 paper “Escaping Model Collapse via Synthetic Data Verification”](https://proceedings.iclr.cc/paper_files/paper/2026/hash/29806b2e4dcb35e42abed21d43e2b7d8-Abstract-Conference.html) studies a simple but important intervention: use an external verifier—human or stronger model—to guide synthetic retraining. The paper reports near-term improvements under its theory and experiments, while also warning that an imperfect verifier can cause gains to plateau or reverse.

That caveat is the architecture.

## A generator is a biased sampler

Every generator has preferences. It may produce fluent, common, easy-to-score examples more often than ambiguous or rare cases. A second generation pass tends to reproduce the first model's representation of the world. Repeatedly training on those samples can narrow the distribution even when the dataset keeps growing.

The danger is subtle because aggregate metrics can remain stable while coverage deteriorates:

- rare failure modes disappear;
- unusual phrasing is normalized away;
- minority or low-frequency cases are underrepresented;
- examples become too easy for the current verifier;
- the model learns the generator's stylistic habits.

Synthetic data is not new information by default. It is a transformation of information the generator already has, plus whatever constraints and external evidence the pipeline introduces.

## Verification is an information source

A verifier does more than remove bad rows. It changes which information survives into the next training round.

A useful verifier can evaluate:

- correctness against a trusted source;
- task-specific constraints;
- diversity relative to the current corpus;
- novelty and coverage;
- provenance and policy;
- calibration or uncertainty;
- downstream utility after training.

The verifier may be a human, a stronger model, an execution environment, a simulator, a test suite, or a combination. The important property is independence from the generator's blind spots.

If the same model generates and approves the data, the loop can become self-confirming:

~~~text
generator -> examples -> same-model judge -> training
     ^                                  |
     +----------------------------------+
~~~

The system may improve on its own judge while degrading on the real task.

## The data pipeline should preserve provenance

Every synthetic example should carry lineage. A training record without lineage is hard to debug and impossible to selectively remove.

~~~ts
type SyntheticExample = {
  id: string
  sourceRefs: string[]
  generator: {
    model: string
    version: string
    promptTemplate: string
    seed?: number
  }
  verifier: {
    verifierId: string
    decision: "accept" | "reject" | "review"
    score?: number
    evidenceRefs: string[]
  }
  distributionTags: string[]
  privacyClass: "public" | "internal" | "restricted"
  createdAt: string
}
~~~

The fields are deliberately more operational than scientific. They let a team answer:

- Which model created this example?
- What source or constraint shaped it?
- Which verifier accepted it?
- Where is the evidence?
- Which training runs included it?
- Can it be removed without rebuilding the entire corpus?

Provenance turns synthetic data from an anonymous blob into a controllable production artifact.

## A verification loop has different gates

Do not reduce verification to one quality score. Use a sequence of gates with different failure semantics:

1. **Schema gate.** Is the example structurally valid?
2. **Policy gate.** Is it allowed to be stored and used?
3. **Grounding gate.** Does it agree with trusted evidence or executable behavior?
4. **Diversity gate.** Does it add useful coverage rather than a near-duplicate?
5. **Risk gate.** Does a human need to inspect it?
6. **Holdout gate.** Does a small training trial improve the real evaluation set?

The first gates are cheap. The last gate is expensive but decisive.

~~~text
generate
  -> parse
  -> policy filter
  -> evidence verify
  -> diversity and coverage check
  -> human review for high-impact cases
  -> train a small candidate
  -> evaluate on held-out human data
  -> promote or roll back
~~~

Promotion should be reversible. If the next model is worse on a rare-case holdout, the pipeline must be able to identify the synthetic batch that changed the result.

## Diversity needs a target

“More diverse” is not a measurable requirement until the team defines the dimensions that matter.

For a coding model, diversity might include:

- languages and frameworks;
- repository sizes;
- error types;
- code style;
- dependency topology;
- test strategy;
- incomplete or contradictory requirements.

For a support system, it may include customer vocabulary, languages, accessibility needs, emotional tone, and uncommon account states.

Use distribution reports that compare:

- trusted human data;
- current training data;
- newly generated candidates;
- accepted synthetic data;
- rejected and review queues;
- downstream evaluation slices.

The goal is not to copy the human distribution exactly. It is to know which distribution is being changed and why.

## The verifier can become the new bottleneck

Verification does not make data free. A human review queue can become expensive. A stronger model can cost more than the generator. A simulator can be slow. An execution-based checker can require a sandbox and external dependencies.

That cost is often justified because bad training data is a compounding error. But the pipeline needs an economics model:

~~~text
accepted_value =
  evaluation_gain
  - generation_cost
  - verification_cost
  - training_cost
  - regression_risk
~~~

Prefer targeted verification for high-value uncertainty:

- verify rare or risky examples deeply;
- sample easy examples;
- use cheap structural checks before expensive semantic checks;
- route disagreements to humans;
- spend more verification budget where the model's behavior matters most.

The objective is not maximum acceptance. It is maximum reliable learning per unit of verification.

## Holdouts must remain human-owned

If the evaluation set is generated by the same system as the training set, the pipeline can report improvement while moving away from reality.

Protect a human or independently sourced holdout:

- keep it out of prompt templates;
- avoid using its exact wording for generation;
- track contamination from generated derivatives;
- evaluate on rare slices, not only a global average;
- rotate some challenge sets without exposing them to the generator;
- record which improvements replicate across holdouts.

The holdout is not a museum piece. It is a measurement instrument. Its job is to reveal when the synthetic loop is learning the evaluator rather than the task.

## Verification can include execution

Many technical tasks have a better verifier than another language model:

- compile the code;
- run the tests;
- execute the SQL against a fixture;
- render the UI;
- validate a JSON schema;
- replay an API request in a sandbox;
- compare a generated plan against a simulator.

This gives the pipeline grounded feedback. It also creates an opportunity for adversarial examples: generate cases that deliberately stress the verifier and then strengthen the verifier where it fails.

The execution environment must be isolated. A synthetic data pipeline that runs untrusted generated code without limits can turn a quality-control system into a security problem.

## Why the current market cares

As models become part of data-generation pipelines, the scarce asset is not only GPU time. It is reliable signal. Organizations need training data that can be explained, audited, removed, and shown to improve a real task.

That favors platforms with:

- dataset lineage;
- evaluation slices;
- independent verifiers;
- human review routing;
- contamination checks;
- reversible dataset versions;
- cost-aware promotion;
- reproducible training manifests.

The same infrastructure supports reinforcement learning, code generation, agent traces, and domain-specific synthetic data. It is a data platform problem with a model in the loop.

## The senior-engineering rule

Never ask only whether a generator can produce enough examples. Ask what prevents the next model from becoming a better copy of the generator's blind spots.

A durable synthetic-data system:

1. preserves source and generation lineage;
2. uses verifiers that add independent information;
3. measures diversity and coverage explicitly;
4. protects human-owned holdouts;
5. evaluates small candidate training runs before promotion;
6. keeps every dataset version reversible.

Scale matters, but feedback quality matters more. The generator makes data abundant. The verification loop determines whether abundance becomes learning or collapse.
