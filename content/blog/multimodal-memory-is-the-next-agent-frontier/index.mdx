RAG gave AI systems a useful answer to a narrow problem: how do we retrieve relevant information that does not fit in the model's context window?

Persistent agents need a broader answer. They need to remember what happened, what was learned, which visual state mattered, which decisions were provisional, and how those memories should change after a new interaction. A vector index is part of that system, but it is not the system.

The frontier is becoming multimodal memory.

The [MSM-Mem research paper](https://arxiv.org/abs/2608.21810), published in August 2026, describes a multimodal medical-agent memory with semantic, episodic, and visual components that update incrementally across interactions. The domain is medical, but the systems lesson generalizes: an agent's memory should preserve different kinds of evidence instead of flattening every experience into one embedding.

## Three kinds of memory

An agent usually needs at least three distinct memory behaviors:

1. **Semantic memory** stores durable facts, concepts, preferences, and relationships. It answers “what is generally true or useful?”
2. **Episodic memory** stores events, decisions, failures, and outcomes. It answers “what happened, when, and what did we learn?”
3. **Visual or multimodal memory** stores references to images, audio, video, documents, and the observations extracted from them. It answers “what did the world look or sound like?”

The boundaries are not absolute. A meeting recording can produce a semantic fact and an episodic event. A screenshot can establish a visual state and support a later decision. The point is to keep the provenance and behavior distinguishable.

Flattening all of this into one nearest-neighbor index creates predictable problems:

- a stale preference may outrank a recent decision;
- a visual observation may be treated as a verified fact;
- a partial event may look like a complete summary;
- two similar images may be confused without temporal or entity context;
- deleting one memory may leave copies in summaries, embeddings, and caches.

Memory needs types, not just vectors.

## Memory is a write path

Most RAG architectures focus on retrieval. Persistent agents need a write path with its own policy.

A useful memory event includes:

~~~text
event_id
subject and scope
observed_at and recorded_at
modality references
raw artifact location
extracted claims
confidence and provenance
privacy classification
retention and deletion policy
supersedes / contradicted_by links
~~~

The raw artifact should not disappear behind a summary. Summaries are useful for context, but they are lossy transformations. When the agent must explain or correct a memory, the system needs to locate the original evidence.

The write path should also be selective. Recording every token, frame, and tool result makes memory expensive and noisy. A policy can decide:

- what is worth retaining;
- at which abstraction level;
- for which principal or workspace;
- for how long;
- under what consent;
- whether the memory is allowed to influence an action.

This is similar to event sourcing with a learned compaction layer. The compacted memory is useful for retrieval; the event log preserves the ability to inspect and rebuild it.

## Temporal alignment is the hard part

Multimodal memory is not just a set of modality-specific indexes. It needs alignment.

An agent may observe an image, hear a comment, and receive a text instruction within the same minute. Those signals may describe one event. Or they may be unrelated observations from different contexts. Timestamps alone are not sufficient; clocks drift, uploads are delayed, and a single conversation can refer to an older artifact.

Alignment needs multiple signals:

- session and task identifiers;
- capture time and ingestion time;
- entity references;
- spatial or screen location;
- speaker or source identity;
- temporal neighborhood;
- causal links to tool calls or decisions.

The memory system should preserve uncertainty. If an image is probably associated with a ticket but not confirmed, the link should be probabilistic or provisional rather than silently promoted to fact.

## Retrieval becomes a compiler

The retrieval question is no longer “which chunks are close to this query?” It becomes “which memory views are appropriate for this task?”

For a debugging agent, retrieval may need:

1. the latest repository state;
2. previous failures for the same component;
3. the decision that changed the deployment;
4. a screenshot of the failing UI;
5. the raw logs that support the claim.

For a personal assistant, retrieval may need a recent preference, the original event that established it, and a confidence check if the preference is old.

That is closer to a retrieval compiler:

~~~text
task intent
  -> required memory types
  -> scope and permissions
  -> temporal window
  -> evidence level
  -> ranked context package
~~~

The context package should explain what was included and why. This supports debugging and helps the agent avoid confusing a generated summary with primary evidence.

## Consolidation should be incremental

Memory systems often perform a nightly batch job: summarize everything, embed it, and rebuild an index. That is operationally simple but can produce abrupt changes in behavior.

Incremental consolidation is safer. After each meaningful interaction, the system can:

- add a raw event;
- update a small set of claims;
- link the event to related episodes;
- mark conflicts;
- refresh affected summaries;
- schedule deeper consolidation when the cost is justified.

This makes memory evolve rather than reset. The [MSM-Mem paper](https://arxiv.org/abs/2608.21810) emphasizes improvement through continued usage, which is a useful design target: a memory system should get better because it learns from outcomes, not merely because it stores more records.

The risk is self-reinforcing error. A wrong summary can be retrieved, treated as evidence, and strengthened by later summaries. Every consolidation pass should retain provenance and support retraction.

## Action memory needs stronger boundaries

Not every memory should be allowed to drive an action.

A stored preference might choose a display theme. A remembered financial instruction should not authorize a transfer without current confirmation. A previous tool result may be stale. A visual observation may be ambiguous.

Define memory authority separately from memory relevance:

- **relevant:** useful for answering or planning;
- **trusted:** supported by provenance and freshness;
- **actionable:** permitted to influence a side effect;
- **binding:** requires explicit current authority.

This distinction prevents a common failure mode in agentic systems: turning “the agent remembers this” into “the agent may do this.”

## Privacy is a lifecycle, not a checkbox

Multimodal memory increases the number of places sensitive material can exist:

- original media;
- extracted transcripts;
- captions and descriptions;
- embeddings;
- summaries;
- caches;
- evaluation traces;
- backups;
- downstream tool artifacts.

Deletion must propagate across that lifecycle. A user who removes a photo should not need to know whether a caption, embedding, or agent summary still contains information derived from it.

The system also needs access-aware retrieval. A memory may be valid but outside the current workspace, user, or purpose. Scope should be checked before ranking, not after the model has seen the content.

Retention should be tied to the memory's purpose. Keeping every visual frame forever is rarely a reasonable default. Keeping a compact event and a user-controlled link may be enough.

## How to evaluate memory

Memory quality is not recall alone. An agent can retrieve many relevant items and still make poor decisions.

Evaluate at least:

- retrieval relevance by memory type;
- temporal freshness;
- provenance preservation;
- contradiction detection;
- deletion completeness;
- cross-modal alignment;
- action safety;
- memory cost per useful task;
- improvement or degradation over repeated sessions.

Include adversarial cases: stale preferences, similar images, partial recordings, conflicting instructions, revoked access, and a user asking why a memory influenced an answer.

The gold standard is not “the agent remembered more.” It is “the agent remembered the right evidence, at the right scope, and knew when not to act on it.”

## Beyond the vector database

Vector search will remain useful. It is excellent at surfacing semantic neighborhoods. But persistent multimodal memory is a distributed system with an event log, object storage, indexes, compaction, access policy, retention, and observability.

The architecture should make those pieces visible:

~~~text
capture -> event log -> modality storage
                  -> extraction
                  -> typed memory views
                  -> policy-aware retrieval
                  -> agent context
                  -> outcome and correction
~~~

The outcome closes the loop. If a retrieved memory was helpful, stale, or harmful, the system should record that signal. Memory becomes a learning surface for the agent runtime, not a static database table.

The next generation of agents will be distinguished by what they can remember responsibly. The hard problem is not putting embeddings in a table. It is building a memory that can preserve experience without confusing similarity for truth.
